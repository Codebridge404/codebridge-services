# Auth-service security review — 18 November 2026

Scope: local `auth-service`, reviewed at commit `8dd3893`, with emphasis on passkeys, authentication, reauthentication, and existing security regressions. This is a focused review, not a complete platform penetration test. The original audit made no implementation changes; the local remediation is documented below.

## Remediation status — all three findings fixed locally

- Reauthentication verification now uses Laravel's named `reauthentication` limiter: **5 verification attempts per account per 15 minutes**, plus **30 per IP per minute** across accounts. These limits count all verification attempts, including successful ones, before credential checks. The account key uses the authenticated user's ID; changing sessions, IPs, request identifiers, methods, or requesting new options cannot reset the account budget. Blocked requests return HTTP 429, `REAUTHENTICATION_RATE_LIMITED`, `Retry-After`, and a request ID. The API response annotation documents the new limit.
- Enrollment options and verification now require an explicit session identifier. Verification checks the stored account and session before accepting an attestation, for both Sanctum tokens and JWT session families. Challenges remain single use and expire after five minutes. Existing challenges without a session binding are rejected; clients must obtain fresh options.
- Authentication verifies the expected account, preserves the original credential allowlist, and validates supplied user handles. An unknown email cannot turn an identified ceremony into discoverable login. Login without a preselected email remains supported.
- The API exception handler now preserves Laravel's explicit HTTP response exceptions, so the limiter's intended 429 response is not rewritten as an internal 500 error.
- The three audit probes were replaced by **25 automated security regression cases** in `tests/Feature/Security/PasskeySecurityRemediationTest.php`. They cover attack rejection and valid login/enrollment, with production-style exception handling (`app.debug=false`). Existing tests that create enrollment options directly now supply their session binding.

## Original confirmed findings (before remediation)

### 1. Medium: password reauthentication has no application rate limit

Location: `app/Http/Controllers/Auth/PasskeyController.php:422` and `routes/api/auth.php:89`.

`POST /api/v1/auth/reauthenticate/verify` checks the current user's password but does not limit failed guesses. Route inspection confirms that neither `auth_throttle` nor Laravel's throttle middleware protects this endpoint. The login controller's account/IP failure counters are not used here.

Reproduction: using a real Sanctum token for a test account, send 40 wrong passwords to this endpoint. All 40 return HTTP 422 `INVALID_CREDENTIALS`; none returns HTTP 429. The correct password immediately afterward returns HTTP 200 with a `passkey_enrollment` grant.

Impact: someone possessing a stolen authenticated session can repeatedly guess that account's password to cross the step-up boundary and authorize credential enrollment or removal. This requires an existing authenticated session; anonymous password guessing through this endpoint was not demonstrated. An upstream gateway may impose a general request limit; deployed gateway protection was not assessed.

Recommended fix: apply a dedicated reauthentication limiter using server-resolved user identity, with an additional IP limit and HTTP 429/Retry-After responses. Count failures across sessions so rotating a stolen session does not reset the account limit. Add a regression expecting throttling after the allowed failures.

Reference: [OWASP authentication throttling guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling).

### 2. Medium: passkey enrollment loses session binding at verification

Location: `app/Services/PasskeyService.php:170` and `app/Http/Controllers/Auth/PasskeyController.php:83`.

Registration options store `session_id` in the challenge cache after consuming a session-bound reauthentication grant. `verifyRegistration()` checks the cached user and `reauth_authorized`, but never compares the saved session with the session submitting the registration. The controller resolves the submitting session only after the new credential has been stored.

Reproduction: create two distinct Sanctum tokens A and B for the same user. Reauthenticate and obtain enrollment options using A. Submit a valid test attestation with that challenge using B, without reauthenticating B. The API returns HTTP 201 and stores the credential. The probe also verifies that the submitting authenticated token is B and the challenge's saved session is A.

Impact: another session of the same account can use an authorized enrollment challenge if it obtains the challenge ID and challenge value during their five-minute lifetime. This weakens the intended session-specific step-up protection. It does not allow enrollment into another user's account, and obtaining A's challenge material remains a prerequisite.

Recommended fix: pass the server-resolved current session into registration verification and enforce equality with the cached session before accepting the credential. Add tests for A-to-A success, A-to-B rejection, cross-user rejection, expiration, and single use.

### 3. Medium: identified passkey login ignores the challenge's expected account

Location: `app/Services/PasskeyService.php:311` and `app/Services/PasskeyService.php:354`.

Authentication options save the identified account's `user_id` and return its `allowCredentials`. Verification looks up any active credential globally and checks its signature, without checking its owner against the saved `user_id`. The account-scoped credential allowlist is consequently not enforced by the server.

Reproduction: create accounts A and B, each with a passkey. Request options using A's email. Sign that challenge using B's private key and submit B's credential, which is absent from A's returned allowlist. The API returns HTTP 200 and an access JWT whose subject is B.

Impact: the server accepts a different identity from the one selected when the identified ceremony began. This permits account substitution if an attacker can submit their own valid assertion into that flow. The probe logs in as B; it does not obtain access to A or bypass the signature requirement. Discoverable login without a preselected user should remain supported separately.

Recommended fix: if the challenge contains a non-null expected user ID, require the credential owner to match it. Preserve and enforce any credential restrictions from the original ceremony. Validate a supplied user handle against the stored credential/account handle. Add regressions for cross-account rejection and discoverable-login success.

Reference: [W3C WebAuthn assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion), steps 5–6, requires credential allowlist and identified-account checks.

The original audit probes asserted the unsafe behavior and confirmed the findings. They have now been replaced by the ordinary regression tests listed above, which require rejection/throttling and run in the default suite.

Tests use the existing PHPUnit configuration: SQLite `:memory:`, array cache/sessions, and synchronous queues. The application database was not reset or wiped. No production endpoints were exercised. MySQL, Redis/Horizon, MinIO, full cross-service E2E, concurrent load, and deployed configuration were not verified by this review. The default suite explicitly excludes infrastructure integration tests, so its passing result does not establish those integrations are secure.

All implementation and test changes remain local to `auth-service`. No commits, pushes, or pull requests were made.
